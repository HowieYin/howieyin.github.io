文本一模一样，分段编码为什么会换一串 Token？

结论：对现代 byte-level BPE，先拼文本再编码，通常不能用“分别编码后拼 Token”替代。两串 Token 可以解码成完全相同的 UTF-8 字节，甚至 Token 数量也相同，ID 与边界却不同。模型接收的是 Token ID 序列，前缀 KV 复用也必须先比较 Token 前缀。

类型：趣味实验 / Tokenizer 与输入工程。发布与实验：2026-11-16。使用真实 gpt2 和 cl100k_base 编码器，固定 tiktoken 0.12.0；没有运行语言模型、没有测回答质量或服务延迟。主实验的文本字节完全相同；Unicode 一节另讨论“看起来相同但字节不同”。

1｜先猜一下：“hel”加“lo”，应该等于“hello”吗？

字符串拼接当然得到 hello。容易顺手再假设：encode("hel") + encode("lo") 应该等于 encode("hello")。如果成立，就可以把任意收到的文本片段独立编码，再把结果接起来。

实测恰好不成立：

编码器 一次编码 hello 分别编码 hel / lo 后拼接 Token 数
gpt2 [31373] [2978, 5439] 1 vs 2
cl100k_base [15339] [50222, 385] 1 vs 2

两条路径的 Token 字节拼接后都精确等于 b"hello"。变化来自编码边界，不是某个字符被修改，也不是随机性。[2][3]

tiktoken 0.12.0 / cl100k_base 的真实测量。上半例从 1 个 Token 变为 2 个；下半例都为 2 个 Token，但分别是 abc＋de 与 abcd＋e。图中 Token 块之间的边界不属于输入字符。 Open full-size chart ↗

可以把问题写得更精确。令 E 为编码，D_bytes 为先拼 Token 字节再解码的逆过程，|| 表示序列拼接：

E(x + y) ≠ E(x) || E(y)，一般不保持拼接关系
D_bytes(E(x + y)) = D_bytes(E(x) || E(y)) = UTF8(x + y)

可逆保证“能够回到输入字节”，不保证一个字节串只能由一种 Token 序列表示。

2｜BPE 的关键：编码会看见片段边界两侧

Sennrich、Haddow、Birch 的 Neural Machine Translation of Rare Words with Subword Units，University of Edinburgh，ACL 2016，将 BPE 引入子词表示。原论文 §3.2 从字符开始，按训练得到的合并次序组合符号，并限制在词内处理。[1]

GPT-2 的官方编码器进一步使用可逆字节映射：先对文本做正则预分段，再将 UTF-8 字节映射到字节字母表，按词表里的 merge rank 合并相邻符号，最后输出 ID。[2] 本文不是把 2016 字符 BPE 与现代 byte BPE 当成完全相同的实现，也不把 BPE 简化为“从左到右永远选最长词”。

为什么切点会影响输出？把 hel 和 lo 分开提交时，两次编码都没有机会合并跨越切点的符号；一次提交 hello 时，这个边界不存在。正则预分段本身也可能不同，例如空格常与后面的词进入同一片段。

以 cl100k_base 为例，" " + "hello" 整体编码是 [24748]，Token 字节为 20 68 65 6c 6c 6f；分别编码则是 [220,15339]，一个空格 Token 加一个 hello Token。这个观察来自真实词表，不代表所有空白符在所有编码器里都能这样合并。

3｜反直觉再加一层：数量相同，仍然可能不同

cl100k_base 编码 abcde 得到 [13997,451]，对应字节 abc | de。先编码 abcd、再编码 e 得到 [69744,68]，对应 abcd | e。两边都是 2 Token，但 ID 完全不同。

因此只比较 len(ids) 无法判定输入相同，也不能判定前缀缓存可复用。gpt2 在同一个例子里是 2 vs 3 Token，说明结果依赖实际编码器，不能把一个例子的数量当成通用规律。

这也限制了常见的计数办法：把 System Prompt、User Prompt、模板片段分别算 Token 再相加，不一定等于最终输入长度。若实际服务在它们之间插入 Special Token，必须按照那个服务的真实序列结构计算，不能直接套本实验的普通文本拼接。

模型的 Embedding 查表与后续位置基于 ID 序列进行；不同 ID 即使能显示成相同文本，也不能要求中间隐状态相同。本实验没有推断回答一定改变，更没有证明哪个切法更聪明。

4｜完整实验设置：两种编码器、七组切法、85 个切点

环境为 macOS、Python 3.12.2、tiktoken 0.12.0。调用 encode_ordinary，因此只测试普通文本，不加入 Chat Template、Special Token 或模型端预处理。

七组定点实验包括：hel | lo、空格 | hello、abcd | e、hello | 空格world、antidis | establishmentarianism、你 | 好、We say hel | lo。每组都检查两种 Token 路径解码出的字节与原输入一致。

另取九个固定字符串：hello、空格hello、abcde、antidisestablishmentarianism、你好世界、café、12 个 a、The quick brown fox.、1234567890。按 Python 字符串的 Unicode Code Point 枚举所有非空二段切点，合计每个编码器 85 个。

这不是字节随机切分，也不是按 Grapheme Cluster 切分；固定小语料用于找现象和反例，不用于估计真实用户文本的发生概率。结果保存编码词表 rank 与正则表达式的 SHA-256，帮助确认复现配置。

5｜切点扫描：有些串很敏感，有些完全不变

真实扫描结果。标签为“改变 ID 的切点数 / 该字符串全部切点数”，按 Unicode Code Point 切分。蓝色 gpt2、橙色 cl100k_base。长词有更多切点，柱长不能直接当成发生概率。中文案例使用原始的你好世界，图中英文仅作短标签。 Open full-size chart ↗

其中“数量相同但 ID 改变”的切点，gpt2 有 5 个，cl100k_base 有 11 个。特别是 cl100k_base 的数字串，6 个改变 ID 的切点全部保持数量相同。这使只测 Token 数的检查很容易漏掉真实输入变化。

本次所有切点的分段 Token 数相对整体增加量都不为负，但不能据此宣布任意 BPE 编码器、任意字符串都满足同一数量不等式。本文验证的是列出的词表和语料。

6｜明确的反例：分段不一定改变编码

hello | 空格world 在两种编码器中都与整体 hello world 相同。cl100k_base 两条路径均为 [15339,1917]，gpt2 均为 [31373,995]。

antidis | establishmentarianism 这个特定切点也稳定，尽管同一个长词的其他很多切点会改变编码。你 | 好 在这两个编码器中同样稳定。

这些反例说明，正确判断单位是编码器＋完整输入＋具体切点。不能用“英文词内部一定改变”“中文一定不变”或“正好落在某个 Token 后就一定安全”替代实际检查：添加后续文本可能重新改变此前末尾的分段与合并。

7｜前缀 KV Cache：文字前缀不是可复用 Token 前缀

假设此前只收到 We say hel，其 cl100k_base 编码为 [1687,2019,11591]。随后补上 lo，完整文本 We say hello 的编码变为 [1687,2019,24748]。字符前缀全部仍在，但旧的第三个 Token 已被替换。

真实 cl100k_base ID。绿色标示相同的前两个 Token；橙色标示需要重新编码的末尾。可复用前缀为 2 Token，旧第三个 Token 的 KV 不能按整段编码目标直接沿用。 Open full-size chart ↗

若使用同一个因果模型、相同位置与缓存配置，理论上可重用新旧 ID 的最长共同前缀：

r = LCP(E(x), E(x+y))
本例：r = LCP([1687,2019,11591], [1687,2019,24748]) = 2

Token 前缀相同是必要条件；实际还要保证模型权重、位置编码、Adapter、多模态输入和 KV 格式等状态相容。按块缓存的服务也可能要求完整缓存块，因此理论的 2 Token 不保证产生 2 Token 的实际命中。

如果为了保留旧缓存而直接拼 [1687,2019,11591] + [385]，解码仍是同样文字，但你已经改成另一条 ID 序列，不再是“整段重编码”的输入。

这里与 Chunked Prefill 的区别很重要：Chunked Prefill 通常接收已经确定的 Token ID，切的是模型计算轮次；本实验切的是 Tokenizer 的文本输入。前者保留同一 Token 序列，后者可能改变序列。

8｜流式输入怎样处理：末尾未必已经稳定

网络分包、文件读取分块或 UI 逐段输入是传输边界，不能自动当成模型 Token 边界。需要一次性等价的编码结果时，最稳妥的参照是拼好最终文本，调用目标编码器与模板再编码。

长流式输入若不能保留全量重编码，就需要维护可确认的稳定前缀和待处理尾部。tiktoken 0.12.0 提供 encode_with_unstable，返回稳定 Token 与可能补全序列，源码明确将其标为不稳定 API。[3] 它提示了这种问题应在 Tokenizer 层处理，但不是本文已经验证的通用流式编码组件。

不要自行规定“只重编码最后一个字符”或“留固定 3 个 Token 就够”：正则分段与合并规则决定末尾如何变化。本文没有证明一个适用于所有文本和编码器的固定尾窗长度。

训练语料预处理也需要相同的边界约定。按文档插入 Special Token 是明确定义的序列设计；因读取 Buffer 大小变化而意外改变 Token 序列，则会让数据复现依赖 IO 分块。二者应分别记录。

9｜另一个坑：逐 Token 解码可能打碎一个中文字

gpt2 编码 你好 为 [19526,254,25001,121]，每个 Token 的原始字节依次是 e4 bd、a0、e5 a5、bd。其中的单个 Token 不一定是合法、完整的 UTF-8 字符。[2][3]

若对每个 ID 单独调用默认 decode，再拼字符，结果是 ����；先拼原始 Token 字节，再统一解码，得到正确的 你好。cl100k_base 在这个具体例子中 [57668,53901] 各自包含完整汉字，逐个解码没有问题。

raw = b"".join(enc.decode_single_token_bytes(i) for i in ids)
text = raw.decode("utf-8")  # 本实验完整原文的字节序列是合法 UTF-8

所以生成时的逐 Token 显示需要有状态的增量 UTF-8 解码，或暂存未完成字节。不要用每 Token 的替换字符结果判断模型“输出了乱码”；也不要以为任意单 Token 的字节都能独立变成字符。

10｜“看起来一样”还可能是 Unicode 的另一个问题

主实验始终比较完全相同的字节。下面另换一个问题：café 可以使用 U+00E9 的 é，也可以使用 U+0065 U+0301 的 e 加组合重音。这两串 Code Point 和 UTF-8 字节不同，视觉上通常相似。

编码器 NFC café NFD cafe＋组合重音
gpt2 [66,1878,2634]，3 Token [66,8635,136,223]，4 Token
cl100k_base [936,59958]，2 Token [936,1897,54939]，3 Token

Python unicodedata.normalize("NFC", nfd) 在本例中还原为前者，两种编码器归一化后的 ID 因而一致。GPT-2 官方输入流程不自动加上这一步；是否归一化应是输入管线的显式约定。[2][4]

这不是鼓励盲目改写所有输入。代码、精确文本匹配与已有缓存需要统一原始字节约定；规范化也应与模型训练、服务预处理一致。不要把“同一字节串因切点不同而换 Token”和“不同字节串因 Unicode 表示不同而换 Token”混成一个机制。

11｜自己复现与总结：检查 ID，而不只看文字和数量

下载 experiment.py、完整 results.json 与 绘图脚本。首次取得编码词表需要联网；后续可用 tiktoken 的本地缓存。无需模型权重。

python3 -m pip install tiktoken==0.12.0
python3 experiment.py

一个最小玩具复现：

import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
x, y = "abcd", "e"
a = enc.encode_ordinary(x + y)
b = enc.encode_ordinary(x) + enc.encode_ordinary(y)
assert len(a) == len(b) == 2
assert a != b
assert enc.decode_bytes(a) == enc.decode_bytes(b) == b"abcde"
print(a, b)  # [13997, 451] [69744, 68]

真正值得保留的直觉： 字符串、UTF-8 字节与 Token ID 是三个不同层次。同字节保证能还原同文本，同数量只说明长度相同；只有相同 ID 前缀加相容的模型状态，才支持对应 KV 复用。

做输入或缓存排查时，保存目标编码器与版本、最终模板、原始字节、完整 ID 与最长共同前缀。然后再去看模型计算和服务时延。这个小实验不会替你预测回答，但能排除一个很隐蔽的“其实输入变了”。
