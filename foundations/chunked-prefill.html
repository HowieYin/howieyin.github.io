Chunked Prefill：长 Prompt 怎样不挡住别人出字？

结论：Chunked Prefill 把长 Prompt 的前向计算拆到多个调度轮次，让正在 Decode 的请求每轮都有机会继续出字。后续块仍要读取此前块的 KV，因果注意力与完整 Prefill 保持同一计算目标；改变的是调度粒度。块越小，通常越容易控制出字间隔，也越可能增加长 Prompt 的首字等待与执行开销。

类型：基础知识 / Paper 解读 / 推理工程。发布与本地实验：2026-11-16。前置：因果 Attention、KV Cache、Prefill / Decode。证据包括 Sarathi-Serve 原论文、vLLM V1 官方文档和本文 CPU 数值实验；图中的轮次数不是 GPU 时间。

延伸阅读：此前的 PagedAttention 解读主要解释 KV 的存储与管理；Tensor Parallel解释每层通信。本篇补上“同一块 GPU 何时处理哪个请求”的调度问题。KV 分页、计算分块与设备通信可以同时存在，它们处理不同的成本。

1｜一位新客人的长 Prompt，为什么让老客人突然停顿？

假设请求 A、B 已经开始回答，每次前向各产生一个新 Token。这时请求 C 带着几万 Token 的长 Prompt 到来。如果一次完整 Prefill 占据执行资源，A、B 就要等这次计算结束才能继续。

Continuous Batching 允许请求动态加入、退出 Batch，但本身不规定长 Prefill 必须多细。即使把 Prefill 与 Decode 放进同一轮混合 Batch，这一轮也可能因长 Prompt 很慢，A、B 的下一次出字仍会迟到。

因此需要区分两个用户体验指标：

指标 从哪里到哪里 最容易受什么影响
TTFT，Time To First Token 请求到达至第一个输出 Token 排队、Prompt Prefill、首轮输出及服务开销
TBT / ITL 相邻两个输出 Token 之间 每轮执行时间、调度间隔、其他请求干扰
TPOT，Time Per Output Token 通常为首字之后的平均每 Token 时间 平均 Decode 速度；会掩盖个别长停顿

不同论文与服务的计时边界可能不同，要查看定义。P99 TBT 很差而平均 TPOT 尚可并不矛盾：少数长停顿就足以破坏交互体验。Chunking 最直接针对的是这种 Prefill 与 Decode 干扰。[1]

2｜Sarathi-Serve 的设计：把长工作拆成可交错的短轮次

核心论文是 Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve，Amey Agrawal、Nitin Kedia、Ashish Panwar、Jayashree Mohan、Nipun Kwatra、Bhargav Gulavani、Alexey Tumanov、Ramachandran Ramjee；Microsoft Research India / Georgia Tech；OSDI 2024，117–134 页。本文读取 arXiv v3（2024-06-17），重点依据 §4.1–4.3、§5.4.1。[1][2]

作者组合了两个机制。Chunked Prefill 把长 Prompt 分成多个计算块；Hybrid Batching 把这些块与已有 Decode 一起执行。只混合但不切块，轮次仍可能很长；只切块却不让 Decode 加入，也不能充分实现交错服务。

论文 Algorithm 3 的优先顺序是：已有 Decode → 已开始但未完成的 Prefill → 新接纳的 Prefill。调度器给一轮设置 Token Budget，Decode 占用之后，剩余预算再给 Prefill。这避免一个新长 Prompt 把正在生成的请求完全排除在很多轮之外。

论文称它为 stall-free scheduling。这里应理解成避免长 Prefill 造成的 Decode 调度停顿；它不保证每轮耗时完全不增加，也不保证任意到达流量下都满足 SLO。

3｜手算一次调度：预算 5、8、16，到底改变什么？

以下是教学构造与调度计数：一直有两个 Decode 请求 A、B，每轮各处理一个 Query Token；新请求 C 的 Prompt 长度为 12。忽略完成退出、抢占和额外约束，优先给 A、B 各一个 Token。

本轮 Prefill Token 数 c = min(B − D, 剩余 Prompt Token 数)
Prompt 所需轮次 = ceil(P / (B − D))，条件 B > D

这里 B 是本轮 Query Token 总预算，D=2，P=12。若 B≤D，在这个简化优先策略下本轮没有空间推进 Prefill；真实系统还必须考虑准入、容量与公平性。

教学调度图。每个小格是一个计划处理的 Query Token，横轴是调度轮次；格宽不表示执行时长。蓝色为两个 Decode Token，橙色为 Prompt 块，均由公开脚本计数。 Open full-size chart ↗

Budget B 每轮可用 Prefill 预算 C 完成所需轮次 一轮实际 Token 总数
5 3 4 5、5、5、5
8 6 2 8、8
16 14 1 14，只有 12 个 Prompt Token 可处理

较小 B 给 Decode 更多调度机会；较大 B 让 C 更少轮完成。这些数字不能换算成毫秒：处理 5 个 Query Token 并不恒定耗时，两个 Decode Token 各自扫描的历史 KV 长度也可能不同。Budget 限制 Query 数量，不是所有 Attention 乘加、KV 字节或服务请求数量。

4｜分成三块之后，Attention 到底看什么？

把 12 个 Prompt Token 按 4 个切块。第一块 Query 位置 1–4 看 Key 1–4，按因果 Mask 只看自己及更早位置；第二块 Query 5–8 看 Key 1–8；第三块 Query 9–12 看 Key 1–12。

教学因果可见性图。行是绝对 Query 位置，列是 Key 位置。橙色区域来自旧块 KV，蓝色区域来自本块 KV；白色为未来位置。每个 Head 合计仍有 78 对可见 Query–Key。 Open full-size chart ↗

设当前块从 0-based 位置 s 开始，长度 c，单 Head 的维度为 d。每一层得到：

Q_chunk：c × d
K_all = concat(K_old, K_chunk)：(s+c) × d
V_all： (s+c) × d
S = Q_chunk K_allᵀ / √d：c × (s+c)
O_chunk = softmax(S + causal_mask) V_all：c × d

Mask 以绝对 Token 位置判断：第 i 个 Query 只允许 j≤i。旧 KV 不能丢；若使用 RoPE，后续块也必须继续使用原序列的位置。每层保存自己的 KV：浅层旧 KV 不能拿来代替深层旧 KV。

对标准因果网络，可逐层建立等价性：早期 Token 不依赖未来，第一块输出与整段相同；假设此前块每层 KV 都正确，当前块就拥有整段计算中相同的可见 K/V，因此也能得到相同目标输出。真实实现改变 Kernel、归约顺序和浮点精度时，通常只要求容差内一致。

这还解释了与 Online Softmax 的关系：Chunked Prefill 沿 Query / Prompt 进度切分服务工作；FlashAttention 的 Online Softmax 沿 Key 计算块合并一行归一化统计。一轮 Prompt 块内部仍可以使用 FlashAttention，两个“块”不是同一个层级。

5｜计算与显存账本：没有凭空省掉长上下文

对长度 N 的完整因果 Prompt，一个 Head 的有效 Query–Key 对数仍是：

Σᵢ₌₁…N i = N(N+1)/2
Chunking 后：Σ各块 Σ本块 Query i i = 同一个 N(N+1)/2

Dense Attention 的有效算术规模仍 O(N²d)；各 Token 的 Projection 和 FFN 总量也没有因切块减少。实际 Kernel 会按矩形 Tile 计算、Mask 或跳过某些块，所以有效对数不等于精确执行 FLOPs。

普通 MHA / GQA 的最终 KV 容量可写为：

KV Bytes = 2 × L × N × H_kv × d × b

L 是层数，H_kv 是 KV Head 数，b 是每个元素字节数。分块结束时 N 个 Token 的 KV 都在，最终容量不变。更小块可能降低一次的中间激活、临时缓冲压力，但未完成 Prompt 仍持有 KV，更多在途请求也可能提高系统总占用。

在最朴素的“每轮都重新从 HBM 扫旧 KV”模型里，等长 c 块、N=mc，每层累计访问的 Key 位置数约为 c + 2c + … + mc = N(m+1)/2。这只是块级扫描示意，不等于实测 HBM Bytes：FlashAttention 的 Query Tile、Cache 重用和后端布局会改变实际流量。论文 §4.3 指出旧 KV 重访和额外启动可能使 Prefill 变慢。[1]

6｜CPU 实验：切块正确，但“各块独立算”会错

2026-11-16，macOS、Python 3.12.2、NumPy 2.4.6，CPU float64，Seed=20261116。输入为 12×8，两个因果 Attention Block，每层 2 个 Head、Head Dim=4，带 Residual 与 tanh FFN。为了隔离因果缓存机制，省略 Norm、RoPE、Dropout，没有使用真实预训练模型。

将整段前向作为参照，按不同大小逐块推进，在每层保留旧 KV：

1 12 1.3323×10⁻¹⁵ 3072 78

3 4 8.8818×10⁻¹⁶ 3072 78
4 3 8.8818×10⁻¹⁶ 3072 78

例如 Chunk=5 实际是 5、5、2，因此不要求整除。容量为 2×2×12×2×4×8 = 3072 Bytes。若故意让每个 4 Token 块只看自己，最大输出误差升到 3.001154；第一块仍正确，错误从第二块缺失历史信息开始。

脚本检查所有容差、KV 容量和因果对数。它证明这个简化网络的缓存计算正确，不能证明生产 Kernel 的所有位置编码、量化缓存、多模态布局或 GPU 性能。

Combined 相对 Hybrid-only，在这两个工作负载上 P99 TBT 明显更低，但 P50 TTFT 分别从 0.53 增到 0.76、3.78 增到 3.90。相对 Chunks-only，Combined 又同时改善了这两个指标。这支持组合机制协调取舍，不支持“切块让所有延迟都下降”。

论文的整体容量实验还报告，相对当时测试的 vLLM，在指定延迟约束下，Mistral-7B / 单 A100 最高 2.6×，Yi-34B / 双 A100 最高 3.7×，Falcon-180B / 八 A100 最高 5.6×。这是不同模型、并行配置和历史基线的结果，不能当作当前版本直接开一个参数后的收益。[1][2]

8｜今天如何落地：vLLM 的 Budget 是调度参数

截至本文查阅日 2026-11-16，vLLM 的 V1 优化文档说明：可用时默认启用 Chunked Prefill，优先 Decode，再用剩余 max_num_batched_tokens 推进 Prefill；超出预算的 Prompt 自动切块。[3]

官方文档给出的趋势是：较小 Budget 通常有利于 ITL；较大 Budget 通常有利于 TTFT，并可能提高吞吐。这里的原因是减少长 Prompt 被切到多轮的开销，与允许更充分的矩阵计算。具体最优值取决于模型、设备、序列长度和并发量，文档示例不能替代本机测量。

参数 / 机制 它控制什么 常见误解
max_num_batched_tokens 一轮计划处理的 Token 数 当成上下文最大长度
max_num_seqs 一轮的序列数量限制 当成与 Token Budget 等价
KV Cache 容量 / max_model_len 可存储状态与序列长度约束 以为切小块就能免存长 KV
Prefix Cache 复用相同前缀的已有计算 以为 Chunking 自动产生缓存命中

应先固定版本与 Backend，记录 Prompt / Output 长度、请求到达分布、并行配置和计时定义，再扫 Budget。至少同时看 P50/P99 TTFT、P50/P99 ITL、吞吐、峰值 KV 与失败/抢占次数。只看单个请求 Prefill Tokens/s，会漏掉混合服务中其他人的停顿。

9｜GPU、NPU、CPU 与训练：收益边界在哪里？

大 Prompt 的 Projection / FFN 往往适合较大的 GEMM，单 Token Decode 则常受权重、KV 访问与通信影响。混合 Batch 能改善利用率，但同一轮越大，Decode 也可能等得越久。长上下文 Decode 的 KV 扫描不会被 Query Budget 精确约束，所以应按上下文分布实测。

论文 §4.3 提醒 Chunk 大小还要匹配 Kernel Tile；特定配置中 257 Token 块比 256 Token 块运行时间高约 32%。Figure 14 的 Yi-34B / TP2 测量中，512 块的 Prefill 开销至多约 25%，2048 块几乎可忽略。这些例子证明形状与硬件很重要，不能外推为所有模型的固定比例。[1]

Tensor Parallel 每轮仍可能需要集合通信。块过小会反复付启动与通信延迟；CPU 上也可能被小矩阵开销拖慢。NPU 的静态形状、图编译、KV 布局支持必须另查，不能直接照搬 A100 参数。

单用户端侧、没有其他 Decode 竞争时，切块的隔离收益较少；它仍可能有中断响应与临时内存方面的价值。离线大批量任务若只追吞吐，较大块可能更合适；交互式混合负载、Prompt 长度差异很大时，细粒度调度更有意义。

本机制主要面向推理服务。训练需要保存或重算激活并正确回传跨块梯度，不能把推理中的无梯度 KV Cache 直接拿来当训练分块方案。

10｜总结与启发：先问哪个请求在为谁等待

应记住四件事： 切块保持完整因果 KV；Token Budget 约束的是本轮 Query；最终 KV 和有效 Attention 对数没有减少；首字等待、出字间隔与吞吐需要共同评估。

一个实用判断顺序是：先确认是否有长 Prefill 干扰已有 Decode；再检查每轮实际执行时间、上下文长度和 Kernel 形状；最后调整 Budget 与准入策略。若瓶颈是 KV 容量、网络通信或缓存复用失败，Chunking 只能改变调度，仍需要相应的存储、通信和输入处理优化。

值得继续探索的知识节点是 Prefill / Decode Disaggregation、SLO-aware Admission 与公平调度。它们进一步追问：当一个 Budget 仍不够协调所有请求时，是否需要分设备、分资源或改变接纳策略。
