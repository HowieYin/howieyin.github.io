Tensor Parallel：为什么每层 Transformer 都要“开两次会”？

核心结论：Tensor Parallel 把一层的权重和计算分给多张卡，但中间结果并非始终可以独立使用。经典 Megatron 方案让第一层线性投影按输出通道切、第二层按输入通道切，把通信留到“局部贡献必须相加”的位置：Attention 输出投影一次、MLP 输出投影一次。容量可以扩大，单请求 Decode 延迟却未必下降。

类型：基础知识 / AI Infra / 推理工程。发布：2026-11-09。前置：矩阵乘法、Multi-head Attention、基本 GPU 内存概念。本文区分原论文测量、数学推导与本地 CPU 正确性验证；未执行多 GPU 性能测试。

延伸阅读：此前的 GQA 讨论“多少个 KV Head 才够”，FlashAttention 讨论单设备内部如何少读写显存。这次补上设备之间的链路：一个 Token 穿过 32 层时，为什么会有一串必须等待的通信。

1｜先问一个更具体的问题：切开权重后，谁拿到完整答案？

假设一台设备放不下整个模型。把权重分给两张卡，很容易让每张卡各存一半；困难在于下一步计算需要什么形状的结果。

计算 Y = XW 可以沿两种方向切 W。若每张卡负责不同的输出通道，两张卡得到的是 Y 的不同列，拼起来才是完整 Y。若每张卡负责不同的输入通道，每张卡已经输出完整宽度，但它们只是 Y 的部分贡献，加起来才是完整 Y。

这两种结果长得很不一样：一个是“不同字段”，一个是“同一个字段的不同加数”。All-gather 解决收集不同字段，All-reduce 解决把同字段的加数归约后发给所有参与者。误把它们当成可以互换的同步函数，是读并行代码时很常见的错误。

经典方案的巧妙之处是：第一步产生的分片，恰好是第二步需要的分片。 不必在两次 GEMM 之间先恢复完整中间向量。[1][2]

2｜这条路线从哪里来：Megatron 的目标与证据

原论文是 Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism，Mohammad Shoeybi、Mostofa Patwary、Raul Puri 等，NVIDIA；arXiv:1909.08053，首版 2019-09，本文读取 v4（2020-03）。NVIDIA 在 2019-08 的官方介绍已展示同一并行思路。代码为 NVIDIA/Megatron-LM。[1][2][3]

此前 Data Parallel 通常让各设备拥有完整模型、各处理不同训练样本；能增加吞吐，却不能直接解决“单份模型连优化器状态都放不下”。Pipeline Parallel 可以把不同层放到不同设备，但需要处理流水调度和空泡。Mesh-TensorFlow 已探索通用分布式张量计算。Megatron 选择利用 Transformer 的结构，在既有 PyTorch 实现中插入少量通信操作，让层内并行可与数据并行、流水并行组合。

原论文报告：8.3B 模型、512 张 V100、8 路模型并行 × 64 路数据并行，整体训练达到 15.1 PFLOP/s，相对其单卡基线的扩展效率最高约 76%。这是一组训练、模型大小扩展与多种并行组合下的历史结果。不能把它翻译成“同一个模型用 8 张卡，单 Token 就会快 8×”，也不能据此预测今天 PCIe 机器上的 TP 延迟。

更值得长期记住的是切分规律。当前 Megatron Core 官方 API 仍保留 ColumnParallelLinear、RowParallelLinear，说明这条结构化切分路线继续存在；具体通信可以受 Sequence Parallel、后端融合和配置影响。[4]

3｜Column Parallel：按输出通道切，非线性可以留在本地

为避免“行列”与框架存储混淆，全文使用右乘记法：

X ∈ ℝT×H；W₁ ∈ ℝH×F；W₂ ∈ ℝF×H
MLP(X) = φ(XW₁ + b₁)W₂ + b₂

T 是本次参与计算的 Token 行数，例如 Prefill 的若干输入 Token，或 Decode 中多个活跃请求各自的新 Token；H 是 Hidden Size；F 是中间维度；p 是 TP 设备数。这里先假定 F 能被 p 整除。

把 W₁ 的列切为 W₁ = [W₁⁽¹⁾ … W₁⁽ᵖ⁾]。每张卡都有完整 X，却只有 H×(F/p) 的权重：

Z⁽ʳ⁾ = φ(XW₁⁽ʳ⁾ + b₁⁽ʳ⁾) ∈ ℝT×(F/p)

GELU、ReLU、SiLU 都是逐元素函数，所以某个通道的非线性不需要其他设备的通道。这是第一层选列切分的重要原因。若先沿输入维度切 W₁，再分别对局部乘积做 GELU，一般会得到 φ(a)+φ(b) ≠ φ(a+b)：需要先求和，才能过非线性。

列切分得到的分片并不自动需要 All-gather。 官方 gather_output=False 可以让下游直接消费局部输出；若每层线性算完都无条件 gather，就会破坏这套设计的通信优势。[4]

PyTorch 通常存储线性权重为 [out_features, in_features]，与本文 W 的方向转置。因此论文中的“列切 W”可能对应 checkpoint 张量的第 0 轴切分。读实现时先确认乘法约定，再看轴号。

4｜Row Parallel：每张卡输出完整宽度，但只贡献一部分

把 W₂ 沿输入维度分成 p 段，各段形状 (F/p)×H，恰好与 Z 的分片对应：

U⁽ʳ⁾ = Z⁽ʳ⁾W₂⁽ʳ⁾ ∈ ℝT×H
Y = Σᵣ U⁽ʳ⁾ + b₂

这次每张卡输出 T×H，但 U 不是完整答案。各卡只算了 F/p 个中间通道的贡献，必须对这些贡献求和。经典布局用一次 All-reduce，让每张卡都拿到同一个完整 Y，继续做残差与下一层。

一个两卡、单 Token 的手算例子：设中间激活 Z=[1,2,3,4]，W₂ 的四行是 [1,0]、[0,1]、[1,1]、[2,−1]。GPU 0 的局部输出是 [1,2]，GPU 1 是 [11,−1]；完整结果为 [12,1]。把两个局部结果拼成四维向量，显然不能接回原来的二维残差。

输出 Bias b₂ 应在求和后加一次。若每张卡先加完整 Bias 再求和，会把 Bias 加 p 次。这也解释了官方 Row Parallel API 为什么将 Bias 保持为非分片状态，并允许调用方延后融合。[4]

SwiGLU 仍可使用类似组合：

Z = SiLU(XWgate) ⊙ (XWup)；Y = ZWdown

关键条件是 gate 与 up 必须切到同一组中间通道，让逐元素乘法在本地完成。若两路分片索引不同，需要先对齐布局，不能只看每个张量的尺寸相同就认为正确。

5｜Attention 也开一次会：Head 内独立，输出投影再汇合

在标准 MHA 中，不同 Head 使用不同 Q/K/V 投影。把完整 Head 分给设备后，每张卡能够独立算本地 Head 的分数、Softmax 和加权 Value。经典 Head Parallel 布局下，每个本地 Head 仍能访问其全部有效 KV 位置；没有把上下文长度也切开。[1]

以 8 个 Head、TP=2 为例，每卡负责 4 个 Head。每卡产生 T×(H/2) 的 Head 输出，WO 沿对应输入通道切开，得到 T×H 的部分和，再归约：

O = Concat(O₁,…,Oₕ)WO = Σᵣ O⁽ʳ⁾WO⁽ʳ⁾

所以一个标准 Transformer Block 中，Attention 的 WO 后一次、MLP 的 W₂/Wdown 后一次，前向共两次 All-reduce。QKV 投影内部没有额外必需的跨卡归约，是因为 Head 的计算边界正好落在分片边界上。

GQA/MQA 让事情更有趣：多个 Query Head 共用一个 KV Head，Q 与 KV 的切分粒度不再一致。若 TP 超过 KV Head 数，不能期待 KV Cache 永远再除以 p；后端可能复制部分 KV Head、采用另一种布局，或限制配置。比如 8 个 Q Head、2 个 KV Head、TP=4，一种做法是每卡拥有 2 个 Q Head，但对应 KV 在两卡间重复。是否这样实现必须核查具体后端。

RoPE 通常可在本地 Head 内完成，但配对的旋转通道要同时可用。若进一步切到 Head 内部，之前“无需通信”的前提就需要重新推导。长上下文的 Context Parallel 也属于另一维度的切分，不能套用“本地 Head 已有全部 KV”。

6｜训练为什么又有两次：前向和反向互为镜像

原论文用 f、g 两类操作描述通信：f 前向为恒等、反向为 All-reduce；g 前向为 All-reduce、反向为恒等。一个 MLP 和一个 Attention 块各一对，所以经典 Block 前向两次、反向两次，共四次 TP 归约。[1][2]

直观地看，列切分的第一层前向，各卡都读同一个 X；反向时各分片各自计算 X 的一部分梯度贡献：

dX = Σᵣ dA⁽ʳ⁾(W₁⁽ʳ⁾)ᵀ

每个上游 X 元素参与了所有输出通道，梯度必须相加。第二层输出求和的反向，则把同一个 dY 交给各局部乘积即可。

这里说的四次不包含 Data Parallel 的权重梯度归约、Embedding/词表头、Norm 参数梯度同步、激活重计算或其他布局通信。训练内存也不仅是权重：可切分的大矩阵、梯度和优化器状态大体随 TP 分摊，但复制的激活、残差、通信缓冲和未分片参数仍占空间。

归约次序会改变低精度舍入顺序，数学等价不保证 FP16/BF16 逐 Bit 一致。故比较 TP 配置时，应先检查正确性与 Logits 漂移，再比较性能。随机数、Dropout 和初始化的跨分片一致性也是训练实现必须处理的问题。

7｜通信账本：8 KiB 很小，64 次等待却可能很贵

一次典型前向归约的逻辑输入大小为：

M = T · H · s Bytes

s 是归约元素的字节数；假设传输 FP16/BF16 则为 2。权重量化到 INT4，不代表归约也传 INT4。M 是完整激活的大小，不是每卡权重大小，更不是总 KV Cache。

在理想 ring 的 Reduce-scatter + All-gather 中，每个 Rank 发送：

Bytessend, AR = 2(p−1)M/p
TimeAR ≈ 2(p−1)α + 2(p−1)M/(pβ)

α 是每步通信的有效启动延迟；β 是有效链路带宽，单位 Bytes/s。此模型忽略协议、归约算力、链路竞争与复杂拓扑。小消息可能用 Tree 或专用算法，实际框架也可能融合通信；ring 是帮助理解成本的模型，不能当硬件预测器。

下面固定 H=4096、s=2、32 层。每 Rank 只计发送字节，不把接收再加一次，也不乘设备数；每层前向两次归约。 KiB/MiB/GiB 都按 1024 进制。

Token 行数 T 一次归约逻辑输入 M TP=2：32 层发送 TP=4：32 层发送 TP=8：32 层发送
1 8 KiB 512 KiB 768 KiB 896 KiB
32 256 KiB 16 MiB 24 MiB 28 MiB
4096 32 MiB 2 GiB 3 GiB 3.5 GiB

这些是脚本计算的解析字节数，不是 NIC/NVLink 计数器实测。TP=8、T=1 时，32 层逻辑上仍串过 64 次归约；在上述 ring 模型里，每次 14 个步骤，仅启动项的累计就是 896α。这是符号推导，没有给 α 硬套一个毫秒数。

8｜Prefill、Decode 和端侧：瓶颈为什么换了位置？

Prefill 一次处理更多 Token 行，大 GEMM 常能较好利用设备计算资源，分片权重与计算有机会缩短时间；代价是 T×H 归约也变大。长上下文 Attention 另有随上下文增长的计算与内存读写，不能只用线性层账本代表全层耗时。

小 Batch Decode 每请求通常只增加一行 Query。GEMM 变小，权重读带宽、Kernel 启动和串行链路更突出；跨卡多次同步可能吃掉权重分摊的收益。增加活跃请求能让 T 增大并摊薄每 Token 的启动成本，但可能增加排队时间，吞吐提高与单请求 TPOT 改善需要分别测量。

经典 TP 下，一张卡的大矩阵大致缩到 1/p，线性层本地 FLOPs 也大致缩到 1/p，全系统总算术量没有相应变成原来的 1/p。标准 Attention 的总问题规模仍有 Prefill 的二次项、Decode 对历史 KV 的扫描项，只是分给了不同 Head。复制的 T×H 残差不会自动减少；GQA 的 KV 分片收益要看 Head 布局。

如果模型单卡已经放得下，服务吞吐也可能更适合多个 Data Parallel 副本，让各卡处理不同请求。TP 的选择应同时看容量、延迟、Batch 和拓扑，不宜单看 GPU 利用率。

环境 可能收益 应追踪的成本
高带宽 GPU 互联 权重容量和大 GEMM 分摊 Collective 等待、链路竞争、小矩阵效率
PCIe / 跨节点 容量扩展 实际拓扑、Host staging、网络同步与尾延迟
CPU 多插槽 内存容量与计算分摊 NUMA、跨插槽数据移动、线程调度
端侧 GPU / NPU / HTP 混合 分开存放或执行子图 RPC、格式转换、缓冲复制、缓存维护

最后一行尤其不能照搬 NCCL 的代价模型。异构设备算子支持、数值格式与性能常不对称，拆成 TP 可能每层都经过昂贵边界。端侧更值得先验证权重常驻、单设备量化、KV 读取和算子融合，再决定哪种切分真的有收益。

9｜哪些改进改变了“两次会”的形式？

Sequence Parallel 可以在部分残差、Norm、Dropout 区域沿 Token 维度保存分片，用 Reduce-scatter 代替保留完整输出的归约，再在需要完整 Token 行的列并行 GEMM 前 All-gather。Norm 此时对本地 Token 的完整 H 通道计算，不是随意对 H/p 做 RMSNorm。若 Hidden 维度仍被切开，统计量可能另需通信。[4]

因此“每层两次 All-reduce”是经典复制残差布局的结论，并非所有配置的操作计数。All-reduce 的数学结果可由 Reduce-scatter 与 All-gather 组合得到，但中间布局、时间点和重叠机会不同；将两个名字替换进去不等于通信消失。

训练时，输入梯度归约还可以与本地权重梯度 GEMM 重叠。依赖仍然存在，只是等待部分可能被其他计算覆盖。判断优化要看关键路径上暴露的通信，而不是只看调用有没有标为 async。

Parallel 名称最好与切分对象绑定：

方式 分什么 主要交换什么
TP 同一层的通道 / Head / 矩阵 局部贡献、布局分片
DP 请求或训练样本 训练权重梯度；独立推理副本一般无需逐层同步
PP 不同层 流水阶段边界激活
EP 不同 Expert 路由后 Token 的 Dispatch / Combine
SP / CP 部分区域的 Token / 更完整的上下文 依具体方案 gather、scatter 或 KV/Attention 交换

这些方式可以组合。Embedding、Vocabulary Parallel Softmax、MoE 和更复杂 Attention 的通信还要单独记账，不能把整个推理引擎简化成“层数 × 2”。

下载 完整实验脚本 与 本次 results.json，安装 NumPy 后运行：

python3 experiment.py

精简版前向就是：

parts = []
for rank in range(tp):
    s = slice(rank * F // tp, (rank + 1) * F // tp)
    z = activation(x @ w1[:, s] + b1[s])
    parts.append(z @ w2[s, :])
y = sum(parts) + b2

它在一个 CPU 进程里模拟分片与求和，没有测 Collective 性能。需要多 GPU 复测时，应在相同模型、精度、上下文、Batch 与采样条件下比较 TP=1/2/4/8，分别记录 TTFT、TPOT、吞吐、峰值显存、两类归约耗时以及暴露等待；模型大小固定，才是回答“这个请求有没有加速”。

11｜总结与启发：先标数据布局，再谈设备数量

真正有用的直觉是：每个中间张量都标成“完整复制”“不同通道分片”或“完整宽度部分和”。标清这三类，就能读出大多数 TP 通信为什么发生、能否延后，以及下一步在等谁。

两张卡不是两份独立回答；它们共同完成同一层的一份回答。模型容量与吞吐可以受益，但串行 Decode 需要反复等到贡献汇合。对性能排查而言，最值得追的是 WO → 归约 → 残差/Norm → 下一次投影，以及 Wdown → 归约 → 下一层 这两段依赖链。

下一步可以继续沿知识树研究：Context Parallel 如何交换 KV、MoE 如何把通信移到 Token 路由、Sequence Parallel 如何减少复制激活。这些是在新的张量维度上重新安排计算与通信，而不是再把设备数量乘一次。
